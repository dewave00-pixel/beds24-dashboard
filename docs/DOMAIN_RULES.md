# 도메인 규칙

## 1. 목적

이 문서는 예약, 호실, 날짜, 금액, 수수료, 분석 계산에서 반드시 확인해야 하는 비즈니스 규칙을 정리한다.

코드의 현재 값은 `app/config.ts`, `app/types.ts`, `app/utils/bookingUtils.ts`, `app/utils/analyticsCalculations.ts`가 기준이다. 이 문서는 변경 판단을 돕는 설명이며, 구체적인 수치는 코드와 함께 확인한다.

## 2. 예약 원본과 내부 모델

- Beds24 예약 ID는 예약의 외부 원본 식별자다.
- `Booking`은 화면과 계산에서 사용하는 현재 내부 형태다.
- Beds24 `raw_data`를 UI 여러 곳에서 직접 해석하지 않도록 경계에서 필요한 필드를 정규화한다.
- `propertyId`와 `propId`처럼 하위 호환 필드가 공존한다. 제거 전 모든 호출자와 저장 데이터를 확인한다.

## 3. 활성 예약

다음 상태는 활성 예약에서 제외한다.

```text
cancelled
deleted
inquiry
```

- 상태 비교는 현재 소문자·trim 정규화를 유지한다.
- 새로운 Beds24 상태를 발견하면 표시·분석·동기화·삭제에 미치는 영향을 함께 검토한다.
- 빈 상태를 임의로 취소로 판단하지 않는다.

## 4. 숙소·객실·유닛

`app/config.ts`의 `PROPERTY_GROUPS`가 현재 화면용 숙소·호실 매핑 기준이다.

용어:

- `propertyId`: Beds24 숙소 식별자
- `roomId`: Beds24 room type 식별자
- `unitId`: 동일 room type 안의 실제 배정 유닛
- `unitKey`: 애플리케이션에서 사용하는 안정적인 호실 키

불변조건:

- 여러 실제 호실이 같은 `roomId`를 공유할 수 있다.
- `unitId`가 없는 단독 객실과 미배정 예약을 구분해야 한다.
- `unitId = 0` 또는 null은 현재 미배정 의미로 사용될 수 있다.
- `unitKey` 형식을 변경하면 청소 배정과 숙소 정보 키가 함께 영향을 받는다.
- room/unit 매핑을 추측으로 추가하거나 변경하지 않는다.

매핑 변경 전 확인:

1. Beds24 실제 property/room/unit
2. 기존 `bookings`
3. `cleaning_assignments.unit_key`
4. `properties_info.id`
5. 분석의 숙소·호실 그룹
6. 모바일 표시명과 직원 업무 흐름

## 5. 예약 날짜와 겹침

숙박 날짜는 `[arrival, departure)` 반개구간으로 취급한다.

두 예약의 겹침 조건:

```text
arrivalA < departureB && departureA > arrivalB
```

한 예약의 체크아웃일과 다음 예약의 체크인일이 같은 것은 정상 turnover이며 충돌이 아니다.

연박 연장 시에는 기존 `departure`부터 새 `departure` 사이와 다른 활성 예약이 겹치는지 확인한다.

클라이언트 충돌 검사만 신뢰하지 않고 서버에서 다시 검사한다. 동시 요청까지 완전히 막아야 하는 경우 DB constraint 또는 잠금 전략을 별도로 검토한다.

## 6. 시간대

- 운영 기준은 `Asia/Seoul`이다.
- 예약의 `arrival`, `departure`처럼 날짜만 의미하는 값은 `YYYY-MM-DD`로 관리한다.
- Beds24 `bookingTime`, `modified`, 로그 생성 시각 같은 timestamp는 원본 timezone을 확인한다.
- timezone 정보가 없는 Beds24 timestamp를 UTC로 해석하는 현재 호환 로직을 변경할 때 실제 payload를 먼저 확인한다.
- `toISOString()`은 UTC로 변환하므로 KST 날짜 경계에서 하루가 달라질 수 있음을 확인한다.
- 공휴일은 `app/config.ts`의 명시적 목록을 사용하며 연도 변경 시 갱신한다.

## 7. 금액과 수수료

- 현재 금액은 KRW 정수 기준이다.
- Beds24 `price`가 총 판매액인지 정산금인지 OTA별 의미가 다를 수 있다.
- 일부 OTA는 Beds24에 이미 정산금으로 들어오므로 수수료를 다시 차감하지 않는다.
- Airbnb와 Booking.com 등은 `app/config.ts`의 정책과 예약 체결 시각에 따라 수수료를 계산한다.
- 특정 roomId에 별도 수수료율이 적용될 수 있다.
- 직접 수령한 연박 추가금은 현재 플랫폼 수수료 0%로 실수령에 합산한다.
- 기존 notes 태그 `[연박직접수령:<금액>]`는 계산 호환성에 영향을 줄 수 있다.

수수료 정책 변경 전 확인:

1. Beds24가 전달한 금액의 의미
2. OTA 계약 수수료
3. 적용 시작 시각과 timezone
4. 기존 예약과 신규 예약의 구분
5. room override
6. 직접 수령 금액
7. 모든 분석 화면의 공통 계산 함수 사용 여부

수수료 변경에는 적용 직전·직후, override 객실, 0% OTA, 직접 수령 금액 테스트를 추가한다.

### OTA 광고비

- OTA별 CPC는 원/클릭, CPB는 예약 금액 대비 비율(%)의 현재 운영 참고값으로 관리한다.
- CPB는 기존 OTA 수수료 정책에 이미 반영된 값이므로 광고 설정에 기록한 값을 매출에서 다시 차감하지 않는다.
- Trip.com CPC 선충전액은 실제 충전일 기준 광고비 원장으로 관리한다.
- 조회 기간 광고비 차감 후 매출은 `예약 정산 매출 - 해당 기간 Trip.com 충전액`으로 계산한다.
- Trip.com 충전액은 특정 지점이나 호실에 배분할 근거가 없으므로 전체 매출에서만 차감하고, 지점·호실 매출과 ADR에는 임의 배분하지 않는다.
- 광고 설정값과 실제 충전액을 혼합하지 않는다. 실제 현금 차감에는 충전 원장만 사용한다.
- 수수료 정책에 등록되지 않아 `기타`로 분류되는 예약(`apiSourceId` 없음 포함)은 20% 수수료를 적용한다.
- Trip.com, Agoda, Expedia처럼 Beds24에 이미 정산금으로 들어오는 알려진 OTA의 0% 정책에는 기타 fallback을 적용하지 않는다.

## 8. 분석 지표

### 매출

화면이 총 판매액과 실수령 예상액 중 무엇을 표시하는지 명확히 한다. 같은 이름으로 서로 다른 기준을 사용하지 않는다.

### ADR

```text
ADR = 해당 범위 매출 / 판매된 객실 박수
```

분모 0일 때 0 또는 표시 없음 정책을 일관되게 유지한다.

### 가동률

```text
가동률 = 판매된 객실 박수 / 판매 가능한 객실 박수
```

날짜 범위가 inclusive인지 exclusive인지, 전체 호실 수와 운영 제외 객실이 무엇인지 명시한다.

### 기간 비교

- 금액·ADR 증감은 보통 비율 `%`다.
- 가동률 차이는 비율 변화가 아니라 `%p`로 표시할 수 있다.
- 기준 기간이 0일 때 무한대나 `NaN`이 노출되지 않게 한다.

상세 화면 기획은 [ANALYTICS_SPEC.md](ANALYTICS_SPEC.md)를 함께 확인한다.

## 9. 예약 메모와 태그

- `booking_notes`는 Beds24 notes와 별도의 내부 운영 메모다.
- Beds24 notes에 기록되는 데이터와 내부 메모를 혼동하지 않는다.
- 사용자 입력 길이와 허용 태그를 서버에서 검증한다.
- 예약 삭제·취소 시 내부 메모 보존 정책을 임의로 변경하지 않는다.

## 10. 도메인 변경 승인

다음은 사용자 승인 없이 변경하지 않는다.

- 숙소·room·unit 매핑
- 수수료율과 적용 시점
- 실수령 계산 방식
- ADR·가동률·매출 정의
- 예약 상태 필터
- 겹침 판정 공식
- 직접 수령 금액 태그 형식
- 공휴일과 영업일 정책
