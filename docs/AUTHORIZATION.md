# 인증과 권한 정책

## 1. 목적

이 문서는 내부 운영 사용자 인증과 역할별 접근 정책의 기준을 정의한다. UI의 메뉴 표시와 서버 API 권한이 같은 정책을 따르도록 하는 것이 목적이다.

현재 구현이 이 문서와 다를 수 있다. 차이는 즉시 임의 수정하지 않고 기존 의도와 운영 사용자를 확인한 뒤 계획을 제시한다.

## 2. 개념 구분

Authentication:

> 요청자가 유효한 사용자 세션을 가지고 있는가?

Authorization:

> 인증된 사용자가 해당 화면, API, 예약 또는 청소 배정에 접근할 권한이 있는가?

두 검증을 별도로 수행한다. `auth_role` 문자열 존재, 화면 redirect, 버튼 숨김만으로 인증 또는 인가를 완료했다고 판단하지 않는다.

## 3. 역할

### admin

- 전체 예약 운영과 분석을 담당한다.
- 예약 호실 변경, 연박 연장, 청소 배정, 숙소 정보 수정 권한을 가진다.
- 체크인 관리와 게스트 케어 정보를 조회한다.

### manager

- 예약 대시보드 조회와 본인 청소 업무를 수행한다.
- 현재 숙소 정보 조회 및 수정 화면에 접근할 수 있다.
- 매출·통계, 전체 청소 배정, 체크인 관리에는 접근하지 않는다.
- `staff_1`은 기존 호환성상 manager와 연결되는 경우가 있다.

### staff

- `staff_2`, `staff_3`, `staff_4` 등 청소 담당자다.
- 본인에게 배정된 청소 업무를 확인하고 완료 처리한다.
- 업무 수행을 위해 숙소·도어락 비밀번호를 조회하고 복사할 수 있다.
- 예약·매출·전체 청소 배정·체크인 관리에는 접근하지 않는다.

새 역할이나 역할 의미 변경은 권한 정책 변경이므로 사용자 승인을 받는다.

## 5. API 분류

### Public API

- 로그인 endpoint
- 향후 공개 고객 체크인 시작 endpoint

요구사항:

- 입력 검증
- Rate Limit
- 일반화된 실패 메시지
- 개인정보 최소 응답

### User Session API

- 예약, 분석, 청소, 숙소 정보, 내부 체크인 관리 API

요구사항:

- 서버에서 Supabase 사용자 세션 검증
- `user_profiles` 기반 역할 확인
- endpoint별 역할 검증
- 본인 청소 등 객체 수준 권한 검증

### Internal Job API

- 전체·증분 동기화
- Vercel Cron

요구사항:

- Cron secret 또는 검증된 admin 세션
- 호출 목적별 endpoint 또는 method 구분
- GET mutation 최소화
- 반복 호출과 Beds24 rate limit 방어

### Webhook API

- Beds24가 호출하는 예약 변경 webhook

요구사항:

- 사용자 세션을 요구하지 않는다.
- Beds24가 지원하는 검증 방식 또는 별도 secret을 사용한다.
- payload 검증, 크기 제한, 멱등성을 적용한다.

## 6. 세션 원칙

- Supabase Auth 세션을 서버가 검증할 수 있어야 한다.
- 역할만 담긴 독립 쿠키를 최종 인증 근거로 사용하지 않는다.
- 페이지 redirect는 빠른 optimistic check로 사용할 수 있지만, 민감한 데이터와 mutation은 Route Handler에서 다시 검증한다.
- 인증 상태 변경과 권한 변경을 세션에 반영할 방법을 제공한다.
- 세션 만료 시간을 명시한다.
- 로그아웃 시 현재 세션을 서버와 브라우저에서 무효화한다.
- session/access/refresh token을 `localStorage` 또는 `sessionStorage`에 직접 저장하지 않는다.
- Cookie는 `HttpOnly`, 운영 환경 `Secure`, 적절한 `SameSite`, `Path`, 만료 설정을 검토한다.
- 세션을 갱신할 때 다른 사용자의 응답에 캐시되지 않도록 authenticated route의 캐시 정책을 확인한다.

## 7. 역할 판정

권장 우선순위:

```text
검증된 Supabase 사용자
    ↓
user_profiles의 role / staff_id
    ↓
명시적으로 승인된 기존 계정 호환 fallback
    ↓
권한 거부 또는 최소 권한
```

- 클라이언트가 전달한 role을 신뢰하지 않는다.
- username 문자열만으로 권한을 부여하지 않는다.
- 기존 짧은 아이디 UX를 유지하더라도 서버에서 인증된 사용자 email/profile과 연결한다.
- profile이 없을 때 적용할 fallback은 마이그레이션 기간과 제거 조건을 문서화한다.

## 8. 객체 수준 권한

역할 검증만으로 충분하지 않은 예:

- staff가 특정 `cleaning_assignment`를 완료 처리
- 공개 고객이 특정 reservation을 조회
- 특정 사용자에게 허용된 숙소만 조회

검증 순서:

```text
Authentication
    ↓
Role Authorization
    ↓
Resource Ownership / Assignment
    ↓
Business Rule Validation
    ↓
Data Access
```

클라이언트의 `bookingId`, `staffId`, `reservationId`가 현재 사용자와 관련 있다는 주장을 그대로 신뢰하지 않는다.

## 9. 권한 변경 시 검증

- 미인증 요청은 `401`
- 인증됐지만 역할이 부족하면 `403`
- 존재하지 않거나 접근할 수 없는 객체는 정보 노출을 고려해 `404` 또는 `403` 정책을 일관되게 선택
- admin, manager, 각 staff 역할의 성공·실패 케이스
- 만료·폐기된 세션
- 로그아웃 후 재사용
- profile 변경 후 기존 세션의 권한 반영
- UI 메뉴와 API 권한의 일치
